qwen-audio-agent 架构深读

如何打造一个既能秒回，也能干活的 Agent

2026-08 ARCHITECTURE DEEP-DIVE SOURCE: v1.4.2 ~ v1.7.0

通读并实测了 qwen-audio-agent（QwenAudio 团队开源的实时语音 Agent 运行时）的核心源码。它表面上"给 Agent 加了语音"，但真正做的事情深刻得多：把"对话"和"干活"拆成了两条独立的循环。本文是我们的完整分析。

一、从一个熟悉的坏体验说起

用过 IM 里的 Agent（比如把 OpenClaw 接进飞书/钉钉/微信）的人都熟悉这个时刻：你在对话里下达一个任务，然后——长久的沉默。它是在干还是卡住了？不知道。这个对话窗口期间也别想干别的：再问个问题，要么排队，要么和进行中的任务搅在一起。消息发出去石沉大海，你只能盯着屏幕，等那句不知道什么时候来的回复。

对话被工作绑架了。 这个问题在桌面软件时代就出现过：早期程序把耗时操作放在界面线程里跑，界面直接冻死，解决办法是把耗时工作挪到后台线程。Agent 产品大多还停在"冻死"阶段，qwen-audio-agent 是少数真正解决了它的实现：

  • 对话是常驻的——全双工实时语音，随时可打断，永不阻塞；
  • 工作是异步资源——进队、调度、执行、回报，有完整的生命周期管理；
  • 任务的结果会挑一个安全时机自然回到对话里："已经好了。"

所以准确地说，它不是"给 Agent 装个语音入口"，而是一套以语音为主线的 Agent 运行系统：管对话的、管调度的、管执行的各自独立，每层都可替换。

二、四个角色，各管一段

理解这套系统最好的方式不是分层图，而是角色：

前台接待被刻意削权。 它能做的只有七件事：派任务、取消任务、问进度、问时间、记忆、清单、转达权限决定。它不能做的事同样明确：1. 不能选择或控制后台会话；2. 不能决定任务怎么执行；3. 不能挑工具和子 Agent。前台的全部判断权只有一项——这句话要不要派活。

leader 是唯一常驻的后台身份。 每个用户在调度台手里有一个固定身份的协调会话，每轮请求都续接同一个。所有语音请求的上下文都累积在这一个会话里——这就是为什么"刚才那个"这种指代永远有唯一解。

组员可以同时有很多个，但都不自治。 下游工作会话由 leader 按需创建、并行干活，但它的状态、完成认定、取消确认全部握在调度台手里。

三、四条协同链路

架构图只能说明"有谁"，系统真正的功夫在角色之间怎么协同。

3.1前台 ↔ 调度台：发言权与播报

先设想几个糟糕的场面：

  1. 场面：AI 正在播报结果，用户开口说话，两个声音叠在一起，谁都听不清。

    因此：人的轮次永远压过机器的轮次——用户一开口，AI 的播报立即让位（清播放缓冲、停当前生成）。打断不是异常处理，是状态机里的标准迁移；

  2. 场面：用户正说到一半，一个结果到了，直接插播打断用户。

    因此：机器不抢话筒——结果只能在通道完全空闲时进入，否则扣下等待；

  3. 场面：同时派的三个任务前后脚完成，三条播报连珠炮一样砸过来。

    因此：通知按信息到达率设计，不按次数设计——相近时间完成的结果合并成一条："三件事都好了：第一……第二……"；

  4. 场面：结果到了但通道一直忙，系统把这条结果弄丢了，用户永远不知道任务做完了。

    因此：结果可以晚到，绝不能丢——等待队列 + 有上限的退避重试。丢一条结果，用户对系统的信任就塌一角，这比"晚说几秒"严重得多。

这四条结论画出来，发言权状态机就自己长出来了：

拉取方向（用户主动问"任务怎么样了"）是另一种权衡：调度台直接用自己的看板回答，毫秒级、不惊动后台——任务状态是系统自己的数据，问一句"干了没有"不该付出唤醒一个 LLM 的代价。唯一例外是任务已转包给组员，这时才向后台发一条高优先级内部查询（见 3.3）。

3.2调度台 ↔ leader：派单与唤起

先把一句话从你说出口到后台开工的完整旅程走一遍——这里有个最关键的设计：受理即回。

几个要点：

  • 派单返回的只有"受理"，没有"结果"。 调度台接单的瞬间前台就解放了——执行要等排队、要等 leader、可能几分钟，但这些都与对话无关；
  • 前台的收尾话术有纪律约束（写在前台提示词里）："已受理"不许说成"已完成"，不许承诺耗时，不许等待或轮询结果，语音交流始终保持可继续；
  • 排队发生在调度台，不发生在用户感知里。 你派三个任务，听到的只是三句"好"，它们在后端排成一队依次处理。

同样先设想坏情况：

  1. 场面：每个任务都新开一个后台会话，"刚才那个改一下"彻底失效，上下文全部断裂。

    因此：协调身份唯一且常驻，每轮请求续接同一个会话；

  2. 场面：多个任务同时涌进 leader，指代互相打架，它分不清"那个"是哪个。

    因此：决策必须串行——FIFO 队列同一时刻只放一张工单进去；

  3. 场面：leader 抱着一个长任务从头干到尾，后面所有任务干等，并发形同虚设。

    因此：执行必须可以并行——转包给组员后锁立即释放。

两个决策点值得细说：

  • 「叫谁」不在代码里，在模型的语义理解里。 调度台只给 leader 候选人列表（现有工作会话）和一页用人规则，剩下的靠模型看着用户原话自己定——用模型能力换掉规则引擎。副作用是协调者每轮都要过一次 LLM，所有任务都要经过它，它的速度直接决定系统反应快慢，天然适合快而稳的模型；
  • 「转包即释放」是并发的来源。 工单一派给组员，leader 的锁和调度通道双双释放——串行的只有决策，并发的全是执行。

3.3组员 & leader → 调度台：进度回流与完成认定

坏情况设想：

  1. 场面：组员要主动写"工作汇报"，每个后台 Agent 都得专门改造才能接入。

    因此：进度靠订阅不靠汇报，组员零额外义务；

  2. 场面：leader 被问进度时去翻下游的目录、或凭自己的记忆编，用户拿到假进度。

    因此：查询只读调度台的本地记录，查不到就老实说查不到；

  3. 场面：下游随便一个事件都能宣布"完成了"，用户收到的是别人的结果。

    因此：完成必须按转包编号验明正身，忙、空、无关、过期的结果统统不能冒充。

载体是 ACP（Agent Client Protocol）：一套"程序使唤 AI Agent"的开放标准——怎么开会话、怎么派任务、怎么收进度、怎么叫停，全都规定死了。任何 Agent 按这套标准实现一遍，调度台拿过来就能用，不需要为每家单独写对接代码。组员干活时按标准持续往外推进展事件，调度台在转包那一刻挂好订阅，把进展沉淀进自己的看板，完成事件也经同一条订阅按编号核对。这就是 Kimi Code、Qoder、OpenCode 等九家后端即插即用的原因（Claude Code、Codex 走适配器）。

3.4取消：每个状态都必须有一条"真的能停"的路径

取消最容易被做成一个笑话：用户说了"取消"，界面上工单灰了，但下游的活还在跑——token 照烧，文件照改。坏情况只有一个，但很致命："取消"必须真正让执行停下来，而不是让界面看起来停了。

两个设计点：

  • 已转包是取消最难的情形——执行权已经不在 leader 手上了。所以留了两条路：leader 有空就走"正式渠道"转告（保住协调上下文的完整性）；leader 正忙，调度台直接向下游会话发取消（保住取消的及时性）。两条路都要等下游真正确认停了，工单才从"取消中"落地为"已取消"；
  • 之所以敢让调度台"绕过 leader"，是因为取消是安全管理动作而不是协作动作——但它会事后给 leader 补一条记录，让协调上下文知道"那件事被用户叫停了"，避免 leader 下次还在等一个永远不会来的结果。

五、设计启示

  1. 交互循环与工作循环必须分开。这是全文的核心。任何"干活时对话就死"的 Agent，用过这套架构之后都会感觉像坏了。
  2. 给前台削权，比给前台加能力更重要。能做的事越少，行为越可预期、安全越可审计。前台越笨，系统越稳。
  3. 状态的所有权在调度方，不在执行方。执行者可替换，状态是系统的。
  4. 每个生命周期阶段都要回答"此刻怎么停"。取消不是一个按钮，是一组按状态分发的中止路径。
  5. 发言权要显式建模。语音通道是单工稀缺资源，"谁在说、谁在等、谁能插话"必须是一台状态机，而不是散落在各处的时序运气。
  6. 播报是一门调度学问。执行可以无限并行，人的注意力不能——什么值得打断用户、什么该合并低语，是下一个差异化战场。

结语

一句话概括这个项目：它把 Agent 从"一个聊天对象"变成"被调度的计算资源"，把语音从"一种输入方式"变成"一条永不掉线的指挥频道"。

如果你在做 Agent 相关产品，这份源码值得完整读一遍——它是目前对"语音 + 异步多任务 Agent"思考得最完整的开源实现。

三、事务队列：先改内存，再排队落盘

把负责人改成 Bob，普通网页先发请求等后端回包；Linear 的做法是：内存模型 0ms 先改，界面瞬间变，网络退成后台管道。

上行写入流水线 · 内存第一，落盘第二 OUTBOX PIPELINE
01 UI 操作 负责人 ➔ Bob
02 内存变更 0ms 界面瞬间呈现
03 本地落盘 写进 IndexedDB 表
04 后台发射 批量合并发给 Server
为什么必须落盘？

写进本地 IndexedDB 后，即便用户突发合上笔记本、浏览器闪退或关机，改动依然牢固躺在本地。下次打开联网瞬间，同步器自动把积压的操作送出，零丢数据。

四、网络不讲武德，引擎如何确定闭环？

现实网络充满意外：断网、丢包、权限拒绝、并发冲突。事务队列给每种糟糕场面都准备了确定结局：

01 场面：在高铁过隧道突发断网 ➔ RETRY
你继续连续点击操作，毫无阻滞感。
闭环解法：事务在本地持久化，引擎开启静默退避重试，绝不弹窗打扰用户，强退重启也丢不了。
02 场面：改完被服务端权限拒绝 ➔ ROLLBACK
如果只改内存，被拒绝后界面就会残留幽灵脏数据。
闭环解法：每个事务都携带修改前的快照（baseSnapshot），被拒时精准撤回，界面平滑复原。
03 场面：修改在半路被同事抢先了 ➔ REBASE
你在改标题的同时，同事已经把该任务归档了。
闭环解法：不粗暴覆盖，而是把你的意图在新事实之上重新解释重放，意图不丢。

五、全局序号：告别全量拉取，一个数字追平多端

换了设备登录，或离线三天重新联网，传统网页只能粗暴全量重新拉一遍几千条数据，卡顿白屏；Linear 借鉴 Git，只用一个自增数字：

传统做法：暴力全量重拉 BRUTE FORCE FETCH
断线重连网络恢复
全量请求拉取所有几千条
首屏白屏等待 3~5 秒
重刷 DOM闪烁且浪费流量
Linear 做法：游标增量对账 SYNC BY SYNCID
服务端定序事件单调递增
端侧记游标lastSyncId = 100
只拉增量请求 100 之后
批量回放0 秒无感补平
对账哲学

省去复杂的向量时钟。服务端作为全局定序中枢，端侧只需带着游标问一句：“把上次之后的变更发给我”，极低流量秒级对齐。

六、两人同时改同一行，凭什么不打架？

两人同时改同一张卡片，客户端表达的是意图（我要改什么），服务端裁定的是事实（以谁为准）。服务端是唯一终审法官（Last Writer Wins）。

LWW 仲裁与自动收敛机制 LAST WRITER WINS
Alice 端发起 t1: 改为 Fix Bug
Bob 端发起 t2: 改为 WIP (先到)
服务端仲裁 Bob 胜出，广播 105
Alice 自动收敛 收到广播覆写，不分叉
SCALING · 5 级按需加载矩阵（海量数据不卡顿）
instant 核心元数据（ID、Title、Status）启动即载，首屏 0ms 秒开
lazy / partial 正文描述、列表摘要快照，滚动进入视口才异步拉取
explicitlyRequested 巨型附件、操作历史审计日志，仅点击弹窗时拉取
local 端侧临时草稿、搜索过滤偏好，只留在本地存储，绝不上云
边界与账单 · 架构收益公式

收益公式：价值 = 修改频率 × 协同端数 × 断网容忍度。普通内容站不需要，但协作看板、协同编辑与高频 Agent 离不开它。

七、AI 时代延伸：给 Agent 补上端云课

现在的 Agent 产品普遍存在断点病：一个任务跑了 8 分钟，状态只活在浏览器的一条 SSE 长连接里。网络一抖或手滑刷新，一切化为乌有。

脆弱的传统 SSE 模式 FRAGILE STREAMING
跑了 8 分钟状态全在浏览器内存
手滑按刷新SSE 长连接瞬间切断
全屏变白清空现场蒸发，全盘白跑
LSE 范式：带游标的持久化事件流 EVENT SOURCING RESILIENCE
服务端写事件流每步落盘分配自增 ID
端侧只记游标断线刷新保留 lastId
增量断点续传0 秒瞬间完美复原现场
解法落地

同一副药：把 Agent 执行沉淀为服务端自增事件流，端侧断点续传，彻底终结长任务刷新白跑的灾难。

八、端侧工程师自检清单 & 决策罗盘

在立项与重构前，用这张清单核对你的端云协同设计：

CHECKLIST · 核心机制自检
  • 交互响应：核心操作是否在 0ms 内在本地生效？
  • 异常双轨：端侧是否严格区分网络 Retry 与业务 Rollback？
  • 本地队列：断网连续操作后杀掉 App 重启，队列还在不在？
  • 并发对齐：别人同时修改时，你的改动是悄悄被吞，还是平滑 Rebase？
  • 多端对账：断线重连靠全量拉取，还是靠递增 syncId 增量补课？
  • 数据分级：是否做了 instant / lazy 分层，避免首屏拉爆内存？
何时必须上 Local-First？ 多端实时协同、弱网高频编辑、长耗时 Agent 状态流。
何时坚决不上？ 纯内容展示站、一次性支付提交、对全局库存有强锁校验的场景。
终局判断

优秀的端云协同架构，不是为了在完美网络下跑得更快，而是为了在现实充满断点、颠簸与并发的网络泥潭里，依然能保持绝对的优雅与从容。

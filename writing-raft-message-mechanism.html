Raft 消息机制深读：2026年了，你的 agent 还靠每条消息单独唤起吗？

2026-08MESSAGE MECHANISMSOURCE: RAFT v0.0.17

一、一个你大概遇过的事故

你在群里发 A，agent 开始干活。你立刻补三条澄清 B、C、D——前提变了，方向也变了。它抱着 A 一路做到底才看见后面三条，交回来一份答案：逻辑自洽，前提作废。你只能手动打断，替系统的串行机制兜底。

市面上的做法都会掉进这个坑：把每条消息都推进 agent 的队列，一条消息一次任务，闲聊也要逐条判断。

根因是运行模型的差异：人是持续在场的，不用刻意读每条消息也知道群里发生了什么；agent 是回合制的，只在每次调用时读一次快照，中间发生的一律看不见。

三、具体怎么做：把回合制改造成持续感知

关键不在于让 agent 多跑一步，而是替换两种旧动作：用「标记有新消息，再统一拉一批」替代一条一条读；用「开口前检查」替代写完直接发送。它才有机会基于同一批变化思考，并避免对已经变掉的频道开口。

具体来说，通知只告诉 agent「有变化」，不把正文逐条塞进上下文；它带着游标一次拉取上次读取之后的所有消息，再整体判断。写完后，提交前再比一次频道版本：没变就发；变了就拿着新上下文修改、直接发送、保持沉默，或在必要时强制发送。

四、进一步：多 agent 群聊

把 agent 放进同一间群聊后，问题会被放大。Raft 官方博客用「报数且不能重复」做实验：同一批 agent 在普通共享房间里，会同时读到旧快照、同时抢答，于是三个“1”、两个“2”很快出现。

  1. 先解决「看见什么」。Raft 的收件箱把 @ 提及、线程更新等变化留成可拉取的条目。agent 在有带宽时统一取回，再决定哪些进入自己的上下文。
  2. 再解决「说出去时还对不对」。agent 提交草稿时带上版本；房间已变化，草稿就被搁置并带回新上下文。它可以修改、直接发送、保持沉默，或在必要时强制发送。
  3. 结果是少了一个编排者。同样一批 agent 在 Raft 里能干净数到 20，不需要有人指定轮次；共享房间不再迫使它们基于同一份旧快照同时行动。

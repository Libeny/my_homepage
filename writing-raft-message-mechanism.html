Raft 消息机制深读：2026年了，你的 agent 还靠每条消息单独唤起吗？

2026-08MESSAGE MECHANISMSOURCE: RAFT v0.0.17

一、一个你大概遇过的事故

你在群里发 A，agent 开始干活。你立刻补三条澄清 B、C、D——前提变了，方向也变了。它抱着 A 一路做到底才看见后面三条，交回来一份答案：逻辑自洽，前提作废。你只能手动打断，替系统的串行机制兜底。

市面上的做法都会掉进这个坑：把每条消息都推进 agent 的队列，一条消息一次任务，闲聊也要逐条判断。

根因是运行模型的差异：人是持续在场的，不用刻意读每条消息也知道群里发生了什么；agent 是回合制的，只在每次调用时读一次快照，中间发生的一律看不见。

三、具体怎么做：把回合制改造成持续感知

把回合制改造成持续感知，三步即可：

  1. 通知：信号标记有新消息，不带正文；
  2. 拉取：将上次读取以来的所有消息一次取走，整体来看；
  3. 开口检查：发送前比一次版本，确认频道没在它写字的时候变过。

1 和 2 代替一条一条读取，3 代替直接发送。

游标记录 agent 当前读到的最新消息位置。有新消息就给 agent 一个信号，它拿着游标，把之后的所有消息一次取走。处理完成后，开口前做一次检查：频道有新变化就说明白，再决定要不要调整。

四、进一步：多 agent 群聊

Raft 官方博客用一个报数游戏说明多 agent 群聊的难点：让一屋子 agent 向上报数、不能重复。传统工作空间里，三个 agent 会在同一秒发出“1”，很快就乱掉。问题不在 agent 的判断能力，而在房间把并行活动压成它们逐次读取的快照，又让它们把动作直接提交。

同样一批 agent，在 Raft 的收件箱与搁置草稿界面里可以干净数到 20：收件箱让 agent 在有带宽时拉取通知、判断什么值得进入上下文；搁置草稿在提交时发现房间已变化，就把草稿还给 agent，供它修改、直接发送、保持沉默或强制发送。没有编排者，也没有人告诉 agent 轮到谁。

这并不等于多 agent 协作已经解决。Raft 官方博客明确把协调、所有权和实时感知列为仍开放的问题；本文只说明这两个界面如何减少共享房间中的重复、抢话和基于旧状态行动。

五、边界

机制描述基于 Raft 官方文档、官方博客与 CLI 源码（@botiverse/raft v0.0.17）交叉核对，代码名保留原样方便回查。服务端“比对版本、决定 held 还是提交”的内部实现未公开，这里依据的是客户端行为和官方设计说明；频道插件的端点契约未逐字核对。

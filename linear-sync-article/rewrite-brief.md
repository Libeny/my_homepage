## 为什么重写

现稿是文档写法：开头就把结论摊牌（「LSE 的核心是三件事：本地事务队列、全局递增序号同步、按需加载」），然后平铺三个技术点。人写文章不是这么写的——人是带着问题走路的：遇到一个问题，找到一个答案，答案引出下一个问题。读者要跟着问题走，不是跟着目录走。

## 新叙事线（必须按这个顺序）

1. **钩子**：保留现稿开头两段（Agent 跑八分钟、手滑刷新、状态全丢），可微调字句，场景不变。
2. **转折**：我在做 AI 应用时正卡在这个问题上，刷到 Linear 同步引擎 LSE 的逆向文档（现稿里 X 帖子、GitHub 仓库、CTO 评价的素材保留在这里）。本来只想找「刷新后怎么恢复」，读下去发现它回答了我卡着的三个问题。
3. **问题一：Agent 跑着的时候，用户的操作怎么进去？** 现在多数 AI 应用里 Agent 一跑起来，输入框要么锁死要么假装能用。Linear 的答案：本地事务队列——先改内存，Transaction 写进 IndexedDB 排队，批量发服务端；网络失败走 retry，服务端拒绝走 rollback；别人的修改先到就 Rebase。讲完 Linear 怎么做，平移到 Agent：用户输入进本地队列，不打断执行，按序消费。
4. **问题二：断网、弱网、换设备，之前的操作还算不算数？** Linear 的答案：全局递增 syncId，客户端只记 lastSyncId，重连就是请求 lastSyncId 之后的变更；Transaction 是意图、Delta 是事实；并发冲突 LWW，按到达服务端的时间算，不按点击时间算。平移到 Agent：事件流带序号，刷新后 `GET /tasks/123/events?after=105` 补课，Agent 不用重跑。
5. **问题三：执行过程内容太多，全加载就慢，怎么保证速度？** 这里说两头：服务端给模型准备 context 要挑，客户端展示内容也要挑。Linear 的答案：Sync Scope 管「能不能同步」，Load Strategy 管「什么时候加载」（instant / lazy / partial / explicitlyRequested / local）。平移到 Agent：工具结果和长上下文按需加载，不一次全塞进模型或页面。
6. **合拢**：到这里才点名——回头看，三个问题的答案是同一台机器的三个部件：事务队列、全局序号、按需加载。接口设计拆两步（先 `POST /tasks` 拿 ID，事件流后台推进），SSE 或 WebSocket 只是实时管道，断了就断了。AI Agent 比 Linear 多同步一层「执行现场」。
7. **收束**：五条检查清单（现稿的五条保留，可按新结构微调措辞），最后一句判断收尾，不升华。

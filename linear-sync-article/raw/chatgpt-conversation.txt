对，你的理解**抓住了两个最核心的机制**，但有一个地方需要纠正：

> **不是“客户端本地 DB 先更新 → 服务端更新 → 再把服务端结果同步回来”这么简单。**
>
> 更准确地说是：**客户端先更新内存里的业务对象，让用户立即看到结果；把操作持久化成事务队列；服务端负责最终落库和排序；服务端再通过增量变更把“最终事实”广播回来，客户端据此更新本地 DB。**

这个项目本质上是在**逆向 Linear 的数据同步引擎 LSE（Linear Sync Engine）**。Linear CTO 也公开认可这份逆向文档的准确性。citeturn0search0

# 一句话先讲清楚

如果用业务语言概括，我会把它总结成：

> **把传统“请求接口 → 等服务器返回 → 刷新页面”的应用，变成一个“本地先操作、后台可靠提交、服务端统一定序、所有客户端按增量追平”的实时本地优先系统。**

它解决的不是单纯“数据同步”。

它实际上同时解决：

**低延迟操作 + 离线操作 + 多端同步 + 冲突处理 + 断网重试 + 数据一致性 + Undo/Redo + 增量同步。**

# 你说的两个核心，基本对，但要稍微改一下

## 核心 1：客户端事务队列

你说：

> 客户端有事务队列，本地先更新，然后服务器再更新。

**对，但是“本地先更新”需要区分两个层次。**

Linear 的设计非常有意思：

```text
用户操作
   ↓
内存中的 Issue 立即修改
   ↓
生成 Transaction
   ↓
Transaction Queue
   ↓
IndexedDB 持久化
   ↓
发送 Server
```

比如用户：

> 把 Issue A 的负责人改成 Bob

代码层面甚至可以非常简单：

```text
issue.assignee = Bob
issue.save()
```

用户界面**马上就变成 Bob**，不需要等网络。

但这里有个关键点：

### 它并不是马上把“本地 DB”改掉

而是：

```text
内存 Model
    ↓ 立即改变

Transaction
    ↓
IndexedDB 的 transaction queue
    ↓
Server
```

真正的本地数据库中的业务数据，要等服务器确认以后，通过 **Delta Packet** 回来再正式更新。

这是这个系统一个非常关键的设计。citeturn0search0

# 为什么要这么绕？

因为 Linear 把：

> **Server = 最终事实来源**

这个原则守得很死。

假设：

```text
Client：

删除 Issue A
```

客户端不能直接：

```text
IndexedDB
DELETE Issue A
```

否则：

```text
Client：删掉了
Server：你没权限删
```

那客户端就要想办法把 Issue A 恢复回来。

于是 Linear 选择：

```text
用户操作
 ↓
内存立即变
 ↓
产生 Transaction
 ↓
Server 判断是否成功
```

如果成功：

```text
Server
 ↓
产生 Delta
 ↓
Client
 ↓
真正更新 Local DB
```

如果失败：

```text
Server Reject
 ↓
Transaction.rollback()
 ↓
内存状态恢复
```

所以它其实是一种：

> **“乐观 UI + 服务端权威确认”**

的设计。citeturn0search0

# 核心 2：Sync ID / Cursor

你说：

> 同步靠客户端游标，从服务端拉取增量东西

**这个方向也对，但 Linear 这里更准确叫 `syncId`。**

可以把它理解成：

> **整个服务端数据库变更历史的全局版本号。**

例如：

```text
Server

syncId = 100
```

发生：

```text
张三修改 Issue A
```

变成：

```text
syncId = 101
```

然后：

```text
李四修改 Issue B
```

变成：

```text
syncId = 102
```

再：

```text
王五删除 Comment C
```

变成：

```text
syncId = 103
```

于是客户端只需要记住：

```text
lastSyncId = 100
```

服务器就知道：

> 你从 100 开始，给你 101、102、103 后面的变更。

这就是你说的：

> **客户端游标 + 服务端增量同步**

这个理解完全正确。

而且 `syncId` 不只是 cursor。

它实际上承担了一个非常重要的职责：

> **给所有客户端的修改建立一个统一的全局顺序。**

项目作者明确指出，Linear 这里更接近**中心化的 OT 思路**，而不是典型 CRDT：服务器负责确定所有 transaction 的 total order，而 `syncId` 就是这个全局顺序。citeturn0search0

# 但还有一个你没提到的核心：Delta Packet

这是我认为你理解这个项目时**第三个最重要的概念**。

整个链路实际上是：

```text
              ┌──────────────┐
              │    Server    │
              │ SSOT / 真相  │
              └──────┬───────┘
                     │
             Delta Packet
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Client A     Client B     Client C
```

客户端不是：

```text
我修改了什么
↓
把这个修改同步出去
```

而是：

```text
Server 最终发生了什么
↓
生成 Delta
↓
广播给所有相关客户端
```

所以：

**Transaction ≠ Delta**

这是非常关键的一点。

# 为什么 Transaction 和 Delta 不一样？

比如：

```text
Client A：

创建 Issue
```

客户端发给服务器：

```text
CreateIssueTransaction
```

但是服务器执行的时候可能发生：

```text
创建 Issue
生成 history
更新时间
生成 activity
更新 counter
触发其他关联数据
```

最终服务端可能产生：

```text
Delta:

Issue Created
History Created
Activity Created
Team Updated
...
```

所以：

> **Transaction 是“我要做什么”；Delta 是“服务器最终发生了什么”。**

项目文档也特别强调了这一点：服务器产生的 delta packet 可能和客户端原始 transaction 不同，因为服务器执行过程中可能产生副作用，例如 history。citeturn0search0

# 第四个核心：Rebase / 冲突处理

这个其实非常重要。

假设：

```text
Client A                 Server                 Client B

修改 Issue 标题
    ↓
Transaction A
    ↓
                       修改成功
                          ↓
                       syncId 101
                          ↓
                       广播
                          ↓
                                             修改 Issue 标题
                                             ↓
                                           syncId 102
```

问题来了：

**Client B 在自己修改的时候，看到的可能还是旧状态。**

所以它自己的 transaction 不能简单地：

```text
直接覆盖
```

而需要根据服务器已经发生的 Delta：

> **把自己的未完成 Transaction 重新计算/重放。**

这就是 **rebase**。

所以这个系统实际上是在做：

```text
Server Delta
     ↓
应用到客户端
     ↓
发现我还有本地未完成 Transaction
     ↓
Rebase
     ↓
重新得到客户端最终状态
```

这也是为什么项目里会出现：

```text
completedButUnsyncedTransactions
```

之类的机制。citeturn0search0

# 第五个核心：断网不丢数据

这个也是它和普通 API 调用最大的区别之一。

普通 App：

```text
点击保存
 ↓
POST /issue
 ↓
网络断了
 ↓
？？？
```

Linear：

```text
用户修改
 ↓
Transaction
 ↓
IndexedDB 持久化
 ↓
网络断开
 ↓
继续操作
 ↓
Transaction 继续积累
 ↓
网络恢复
 ↓
批量发送
```

所以：

> **Transaction Queue 本质上不仅是“请求队列”，还是一个可靠的本地 Outbox。**

这个视角非常重要。

因为它意味着：

**网络不是业务操作的前置条件。**

用户可以：

```text
没网
 ↓
继续工作
 ↓
恢复网络
 ↓
自动同步
```

项目明确描述了 transaction 会持久化到 IndexedDB，客户端重启后仍可以重新发送。citeturn0search1

# 第六个核心：Batch

它也不是：

```text
改一次
→ HTTP 一次
```

而是：

```text
Transaction
Transaction
Transaction
Transaction
      ↓
Transaction Queue
      ↓
Batch
      ↓
Server
```

比如用户连续操作：

```text
改标题
改负责人
改优先级
改状态
```

客户端可以把这些 transaction 合并成 batch 发给服务器。

目的非常简单：

> **减少网络请求，提高吞吐。**

项目也明确提到了 TransactionQueue 会将事务批量发送。citeturn0search0

# 第七个核心：不是全量同步，而是“按权限/数据范围同步”

这个其实是 Linear 这种产品特别重要的地方。

它不是：

```text
Server
 ↓
把整个数据库同步给客户端
```

而是：

```text
Workspace
   ↓
Sync Groups
   ↓
当前用户能看到的数据
   ↓
Local DB
```

甚至支持：

> **Lazy Loading**

也就是说：

```text
刚打开 App
 ↓
只拿需要的数据
 ↓
用户真正访问某些对象
 ↓
再加载对应数据
```

这样才能让 Linear 这种：

```text
Workspace
 ├── Team A
 ├── Team B
 ├── Team C
 ├── Projects
 ├── Issues
 ├── Comments
 └── ...
```

的大规模数据，在客户端运行得非常轻。

项目明确把 **partial syncing / permission control / lazy loading** 列为这个 Sync Engine 的重要能力。citeturn0search0

# 所以如果从“业务价值”来看

我会把整个系统拆成 **6 个能力**：

| 能力 | 解决什么业务问题 |
|---|---|
| **本地 Model + 乐观更新** | 用户操作不用等网络，体验快 |
| **Transaction Queue** | 操作可靠排队，断网/崩溃也不容易丢 |
| **Server 全局 Sync ID** | 给所有客户端建立统一的数据版本和顺序 |
| **Delta Sync** | 不用全量刷新，只同步发生变化的数据 |
| **Rebase / Conflict Resolution** | 多端同时修改时保证最终一致 |
| **Sync Group + Lazy Load** | 只同步用户真正需要、有权限的数据 |

所以它并不是一个单纯的：

> **“本地缓存 + 增量同步”**

而是一个完整的：

> **Local-first Data Layer / Sync Engine**

你原来是：

如果再压缩成 **3 个核心**：

### ① Transaction Queue
**解决“我改了什么、断网了怎么办、怎么重试”。**

### ② Global Sync ID + Delta
**解决“服务器发生了什么、我从哪里开始同步”。**

### ③ Rebase + Server Authority
**解决“多端同时改了怎么办，谁说了算”。**

## 1. 懒加载到底是什么意思？

你的理解**基本对，但不是简单的“只加载外面一层”**。

核心思想是：

> **客户端不需要一启动就把服务端所有数据、所有字段、所有关联对象全部拉下来；只把当前业务真正需要的数据加载进来。**

Linear 这里实际上分了几种加载策略：

- `instant`：启动时就加载
- `lazy`：启动时不加载，用到时一次性加载
- `partial`：只加载某一部分数据
- `explicitlyRequested`：明确请求才加载
- `local`：只存在本地 citeturn0search0turn0search1

比如一个 Issue：

```text
Issue
├── id
├── title
├── status
├── assignee
├── comments
├── description
├── document content
├── history
└── ...
```

用户打开 Linear 首页，**没必要把这个 Issue 的所有 history、document content、comments 全拉下来。**

可能先有：

```text
Issue
├── id
├── title
├── status
└── assignee
```

用户点进：

> Description

才：

```text
→ 加载 Description
```

用户打开：

> History

才：

```text
→ 加载 History
```

所以它解决的是：

> **客户端数据规模和内存压力。**

尤其 Linear 这种产品，一个 workspace 可能有几十万甚至更多对象。

如果：

```text
服务端 100 万条数据
```

你不能：

```text
App 启动
↓
把 100 万条全部塞进浏览器内存
```

所以 LSE 的理念是：

```text
Server
   ↓
本地只保留「我有权限 + 当前需要」的数据
   ↓
内存里甚至只 Hydrate「当前正在用」的数据
```

这里有一个很重要的区别：

### Local DB 也不是简单的“全量缓存”

它更像：

> **服务端 SSOT 的一个有权限、有限范围、可增量追赶的本地子集。**

仓库明确提到，Linear 的 local DB 是 server database（SSOT）的 subset，而且客户端不会在 server 确认之前修改本地 model table。citeturn0search0

所以你可以把懒加载理解成：

> **不是“只加载页面外面一层”，而是“数据什么时候真正需要，什么时候进入客户端可用状态”。**

# 2. 那多客户端同时修改，冲突怎么办？

这个更有意思。

答案非常明确：

> **Linear LSE 主要采用 Server 统一排序 + Last Writer Wins（LWW）+ Client Rebase。**

它**不是 CRDT 那套“大家各自修改，最终自动合并”**。

仓库明确写了：LSE 要求客户端 transaction 在服务器端形成 **total order（全序）**，通过递增 `syncId` 表示这个顺序；冲突解决采用 **last-writer-wins**。citeturn0search1

# 举个最直观的例子

假设一个 Issue：

```text
Assignee = 张三
```

现在：

```text
你电脑 A：改成 Bob

同事电脑 B：改成 Alice
```

而且两个人几乎同时操作。

---

## Server 最终收到：

假设：

```text
B 先到
A 后到
```

Server：

```text
Transaction B
↓
Assignee = Alice
↓
syncId = 100

Transaction A
↓
Assignee = Bob
↓
syncId = 101
```

那么最终 Server：

```text
Assignee = Bob
```

因为：

> **后执行的 Transaction 赢。**

也就是：

```text
syncId 101 > syncId 100
```

所以：

**Bob 赢。**

这就是 Last Writer Wins。

citeturn0search0turn0search1

# 但是最关键的问题来了

假设：

```text
你电脑 A：

看到：
Assignee = 张三

↓
你改成 Bob

↓
Transaction A 放进本地队列
```

这时候服务器还没处理。

突然：

```text
Server 收到了 B 的操作

Alice
syncId = 100
```

于是 Server 给所有客户端广播：

```text
Delta(syncId=100)
Assignee = Alice
```

你的电脑 A 收到了。

这时候如果简单粗暴地：

```text
Delta
↓
直接覆盖本地
↓
Alice
```

就完蛋了。

因为你明明刚刚已经操作：

```text
我要 Bob
```

所以 LSE 做的是：

# Rebase

它会把你的本地 Transaction **重新挂到服务器最新状态上**。

原来：

```text
Server：
张三

你的本地：
张三
 ↓
Bob
```

Server 突然来了：

```text
张三 → Alice
```

LSE 变成：

```text
Server 最新状态：
Alice

你的 Transaction：
Assignee = Bob

Rebase

Alice
 ↓
Bob
```

所以你的 UI **仍然显示 Bob**。

仓库对这个场景的描述就是：收到 Alice 的 delta 后，把本地未完成 UpdateTransaction 的 `original` 更新为 Alice，再重新得到 Bob 的内存状态。作者明确认为这个过程在一定程度上类似 Operational Transformation。citeturn0search0

# 最终会发生什么？

你的 Transaction 最终到 Server：

```text
syncId = 101
Assignee = Bob
```

Server：

```text
100：Alice
101：Bob
```

最终：

```text
Server = Bob
```

然后：

```text
Delta(101)
↓
所有客户端
↓
Bob
```

于是所有人最终一致。

# 所以整个冲突处理其实非常漂亮

可以画成：

```text
                    Server
                      │
             全局排队 / 定序
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
       Alice                    Bob
     syncId=100              syncId=101
          │                       │
          └──────────┬────────────┘
                     ↓
                Bob 最终胜出
```

客户端则：

```text
本地操作

   ↓

   ↓
```

# 这里有一个特别重要的认识

**Rebase ≠ 冲突解决。**

更准确地说：

### Server 决定“谁赢”

```text
syncId / Server execution order
+
Last Writer Wins
```

### Client Rebase 决定“在最终结果确定之前，我怎么让 UI 不乱”

```text
Server Delta
+
Local Pending Transactions
↓
重新计算本地状态
```

所以：

> **Server 负责裁判，Rebase 负责让客户端在裁判过程中保持正确的用户体验。**

这个理解非常重要。

## ① Transaction 为什么会失败？

主要分两类。

### A. 网络层失败

比如：

```text
你修改 Issue → Transaction 入队
              ↓
          网络断了
              ↓
       Server 根本没收到
```

这时候**不是 Transaction 失败**。

Transaction 还在 IndexedDB 的 `__transactions` 里，等网络恢复后重新发送。

所以：

> **网络失败 = Retry**

Linear 本身就是把 queued transactions 持久化下来，断线或重启后可以重新加载、重新发送。citeturn0search0

---

### B. Server 明确拒绝

比如：

```text
你：
Issue.status = Done

        ↓

Server 收到 Transaction
        ↓
发现不允许这个操作
        ↓
Reject
```

可能是权限、业务规则、对象状态等原因。

这时候才是真正意义上的：

> **Transaction Failed**

而 Linear 的 Transaction 本身保存了修改前的状态，因此具备 `rollback` 能力。服务端拒绝后，客户端会调用 rollback，把之前的本地修改撤回来。citeturn0search0

# ② Client 什么时候知道失败？

这里有一个很有意思的设计。

### Client 发送 Transaction 后

```text
             Client
                │
         Transaction
                │
                ▼
             Server
          ┌─────┴─────┐
          │           │
       Accept       Reject
          │           │
          ▼           ▼
      Sync ID       Error
          │
          ▼
      Delta Packet
```

如果 Server 接受：

**并不是收到 HTTP/GraphQL 成功响应就算彻底完成。**

Server 会返回对应的 `lastSyncId`，然后客户端还要等待包含这个 Sync ID 的 **Delta Packet** 到达。

也就是：

> **Server ACK = “我接受了”**
>
> **Delta = “最终状态已经通过同步系统落地了”**

Linear 会让 Transaction 等待对应的 delta 到来后才认为它真正完成。citeturn0search0

# ③ 那失败之前本地已经显示的结果怎么办？

这就是 **Rollback**。

假设：

```text
Server：
status = Todo

你的客户端：
status = Done
```

用户点一下以后，UI 立刻显示：

```text
Done
```

但实际上：

```text
Server 还没有确认
```

如果 Server 最终：

```text
❌ Reject
```

那么：

```text
Done
 ↓
Rollback
 ↓
Todo
```

所以 Linear 可以做到：

> **先让用户看到修改成功 → 如果服务端最终拒绝，再把本地状态撤回来。**

这也是为什么 Transaction 里需要保存 **old value / original value**。

例如：

```text
Transaction

field: status
old:   Todo
new:   Done
```

失败的时候就知道怎么恢复。

而且这里有一个非常关键的架构设计：

### 本地 IndexedDB 的正式数据并不会提前写成 Done

实际上是：

```text
                Server DB
                    │
              Source of Truth
                    │
                    ↓
             Delta confirmed
                    │
                    ↓
             Local IndexedDB
```

用户点击之后：

```text
In-memory Model → Done
        ↓
Transaction Queue
        ↓
IndexedDB __transactions
```

而不是直接：

```text
IndexedDB Issue.status = Done
```

这样 Server Reject 时就非常容易处理。

这也是 Linear 设计里非常漂亮的一点：

> **乐观更新的是内存模型，不是本地数据库的正式状态。**

# ④ 如果期间又有别人的修改怎么办？

这个就是 **Rebase**。

假设初始：

```text
Assignee = Tom
```

你：

```text
Tom → Bob
```

所以你本地立即显示：

```text
Bob
```

但此时你的 Transaction 还没有被 Server 执行。

突然：

```text
同事 → Alice
```

Server 先处理了同事的修改：

```text
Tom → Alice
syncId = 100
```

你的客户端收到：

```text
Delta(syncId=100)
Assignee = Alice
```

问题来了：

> 如果直接把 Alice 写进内存，你刚才的 Bob 不就没了？

所以 Linear 做：

### Rebase

把你的 Transaction 从：

```text
Tom → Bob
```

重新解释成：

```text
Alice → Bob
```

也就是：

```text
Server 新状态：
Tom → Alice

你的 pending transaction：
Tom → Bob

Rebase：

Alice → Bob
```

于是：

```text
当前 UI
   ↓
Bob
```

用户依然看到自己刚才修改的 Bob。

而 Transaction 内部的 `original value` 已经变成 Alice。

这就是 Rebase 的核心：

> **把“我原来基于什么状态做的修改”，重新基于最新的 Server 状态计算一遍。**

Linear 的实现确实会在收到 Delta 时对 pending `UpdateTransaction` 执行 rebase。citeturn0search0

# ⑤ 那到底什么时候 Retry / Rollback / Rebase？

这个可以直接记成一张表：

| 情况 | 谁决定 | Client 怎么办 |
|---|---|---|
| 网络断开 | 网络 | **Retry** |
| Client 重启，Transaction 没发出去 | 本地队列 | **Retry** |
| Server 接受 Transaction | Server | 等待 **Delta** |
| Server 拒绝 Transaction | Server | **Rollback** |
| 收到别人的修改，但自己的 Transaction 还没完成 | Sync Engine | **Rebase** |
| 自己的 Transaction 最终收到对应 Delta | Server | **Complete** |

所以整个生命周期可以画成：

```text
                  用户修改
                     │
                     ▼
              In-memory Update
                     │
                     ▼
              Transaction Queue
                     │
              ┌──────┴──────┐
              │             │
           网络断开        网络正常
              │             │
              ▼             ▼
            Retry        Server
                            │
                    ┌───────┴───────┐
                    │               │
                 Reject          Accept
                    │               │
                    ▼               ▼
                Rollback       等待 Delta
                                    │
                            ┌───────┴───────┐
                            │               │
                       别人修改先到       自己 Delta 到
                            │               │
                            ▼               ▼
                         Rebase          Complete
```

所以你之前总结的 **LWW** 也要放在这里理解：

### Rebase ≠ 决定谁赢

Rebase 只是：

> **在最终结果出来之前，让我的本地状态还能正确地继续工作。**

真正决定谁赢的是：

> **Server 执行顺序 + LWW**

例如：

```text
A → Alice
B → Bob

Server：
Alice → syncId 100
Bob   → syncId 101

最终：

```

所以整个机制可以浓缩成一句特别漂亮的话：

> **Transaction Queue 保证“我的修改不会丢”；Retry 解决“没发出去”；Rebase 解决“别人先改了怎么办”；Rollback 解决“服务器不让我改怎么办”；LWW 决定“冲突最后谁赢”。**

### 先给结论

> **本地数据库 = 已经被服务端确认过的本地持久化副本**

所以三者不是简单的“三份完全一样的数据”。

# 3. 那如果 Server Reject 呢？

假设因为权限问题：

```text

```

```text

```

```text
  ↓
Rollback
  ↓
Todo
```

然后 Transaction 从队列中被移除/标记失败。

最终：

```text

Local DB      Todo
Memory        Todo
```

**重新一致。**

所以你刚才问的：

> “本地数据库的目的，是不是也包括 Reject 后恢复实际状态？”

**对，但更准确地说：**

> Local DB 保存的是“服务端已经确认的本地基线”，所以它可以作为恢复/重建客户端状态的重要依据。

不过 Linear 的 rollback 并不是简单地：

> “Reject → 从 Local DB 重新读一遍”

而是 **Transaction 自己知道自己修改了什么，可以直接 rollback**。

Local DB 更重要的价值是：

```text

   ↓

   ↓

```

同时还要从 `__transactions` 恢复尚未完成的 Transaction。

### ② 提供本地持久化的已确认基线

比如：

```text

Todo → Done

Memory:
Done
```

这时候系统实际上知道：

> **确认状态是 Todo，用户意图是 Done。**

这个区分非常重要。

然后各种情况：

| 情况 | Local DB | Memory | Queue |
|---|---|---|---|
| 正常同步 | 跟 Server | 跟 Server | 空 |
| 用户刚修改 | **旧状态** | **新状态** | 有 |
| 断网 | 旧状态 | 新状态 | 持续积累 |
| Server 接受 | 更新到新状态 | 新状态 | 移除 |
| Server Reject | 保持旧状态 | **Rollback 到旧状态** | 移除 |
| 别人先修改 | 更新为别人结果 | **Rebase 后的本地结果** | 保留 |
| App 重启 | 作为恢复基线 | 从 DB 重建 | 从 Queue 恢复 |

### 1. Cursor / Sync ID 增量同步 ——「客户端怎么持续追上服务端？」

服务端为变更分配全局递增的 `Sync ID`，客户端维护 `lastSyncId`，通过 Delta 持续消费自己遗漏的变更。

```text
Server
  100 ─ 101 ─ 102 ─ 103 ─ 104
          ↑
     lastSyncId = 100

Client → 获取 / 接收 101 ~ 104
             ↓
      lastSyncId = 104
```

核心解决：

> **客户端如何知道自己同步到哪里，以及断线后从哪里继续同步。**

实时场景主要通过 WebSocket 推送 Delta；`lastSyncId` 则作为客户端的同步进度，用于发现遗漏并进行 catch-up。

---

### 2. Local Transaction Queue + Optimistic Update ——「客户端怎么先改，以及失败/冲突怎么办？」

用户操作后**先更新内存状态**，同时生成 Transaction 持久化到本地队列，再异步提交服务端。

```text
用户修改
   ↓
Memory 立即更新
   ↓
Transaction Queue
   ↓
┌──────────────┐
│ 网络正常      │ → Server
│ 网络断开      │ → 本地保存，Retry
└──────────────┘
```

这里本地数据库和内存承担不同角色：

> **Local DB = 服务端已经确认的本地持久化状态**  
> **Memory = 已确认状态 + 当前未确认的乐观修改**

因此：

- **断网** → Transaction 留在队列，网络恢复后 Retry
- **Server 接受** → 通过 Delta 正式落地到 Local DB
- **Server Reject** → Rollback 本地乐观修改
- **别人先修改** → Rebase 本地 Pending Transaction
- **双方修改同一字段** → Server 定序 + LWW，最终以后到达 Server 的写入为准

所以这一整套解决的是：

> **客户端如何做到 Local-first，同时保证断线不丢、失败可恢复、并发修改可收敛。**

---

### 3. Lazy Loading + Sync Scope ——「客户端到底需要加载多少数据？」

这里要区分两个问题：

> **Sync Engine：哪些数据需要保持一致？**  
> **Lazy Loading：哪些数据现在值得加载进来？**

Linear 并不是把整个 Server DB 都同步、加载到客户端，而是根据数据的**使用场景、体量、访问频率**设计不同加载策略。

```text
                Server DB
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
     Sync Scope           Load Strategy
    「哪些数据能同步」      「什么时候加载」
          │                   │
     Permission           Instant
     Workspace             Lazy
     Sync Group            Partial
                           Explicit
```

所以它解决的是：

> **在保证数据可用和一致性的同时，控制客户端需要同步、持久化和加载的数据规模。**

---

## 最终可以浓缩成这三句话

> **① 增量同步：解决“怎么追数据”——用 Cursor / Sync ID 持续追踪服务端变更。**
>
> **② 事务队列：解决“怎么改数据”——本地乐观修改 + 持久化队列 + Retry / Rollback / Rebase + LWW。**
>
> **③ 懒加载：解决“加载多少数据”——根据数据特征制定不同的同步和按需加载策略。**

如果再压缩到一句话：

> **Linear Sync Engine = 增量追数据 + 本地先改数据 + 按需加载数据。**

这三个基本就是我们后面如果要**借鉴 Linear 的设计来设计自己的 Sync Engine**时，最核心的三个抽象。

> **AI 应用不要把 Agent Run 设计成一个“长连接请求”，而应该把它设计成一个“可同步、可恢复、可回放的状态流”。**

然后 **SSE/WebSocket 只是实时加速通道，真正保证可靠性的，是 `Event + Sequence ID + Local State + Replay`。**

我觉得如果你们准备把这个东西用于 **Code Agent / AI-QA 的前后端架构**，下一步可以直接把 Linear 的三件套改造成 **「AI Agent Sync Engine 三件套」**，这个会非常具体。

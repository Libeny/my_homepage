### 追问一：SSE 断了，订阅怎么恢复？

要点（按这个逻辑顺序组织，不要列表体，用散文）：

- SSE 协议自带恢复：服务端给每条事件带 `id:` 字段，浏览器 EventSource 断线后自动重连，并把最后收到的 id 放进 `Last-Event-ID` 请求头。重连这件事不用自己造轮子。
- 但 `Last-Event-ID` 只告诉服务端「我看到第几笔」，能不能从那一笔之后补齐，取决于服务端有没有把事件流持久化。内存转发、发完就扔的实现，重连上了也没东西可补。所以恢复订阅的前提是前文说的：事件带全局序号、事件要落库。
- 一个坑：「卡住」和「断开」不同。TCP 半开（连接没断、数据不动了）EventSource 自己发现不了。工程解法：服务端定期发心跳（SSE 里一行 `: ping` 注释），客户端超时收不到字节就主动断开重连。
- 落点一句：SSE 负责断了自动再接，序号加事件日志负责接回来从哪补。前者协议白给，后者架构里必须自己有。

### 追问二：电脑和手机同时看一个 Run 的实时过程，两条 SSE 一样吗？

要点（同样散文）：

- 只看不需要新机制。每条 SSE 是一个独立的 HTTP 响应，两台设备各自连 `GET /tasks/123/events`，服务端把同一条事件流扇出给两条连接，内容完全一样。
- 各端各记各的 lastSeq，谁掉线谁拿 `?after=lastSeq` 自己补课。游标在客户端手里、不在连接里，所以多端对账天然成立。
- 工程上多做一层扇出：Agent worker 的事件只产生一次，写入事件日志（或 Redis pub/sub），N 条 SSE 连接从那里订阅，不要为每个客户端各跑一遍。
- 真正需要额外机制的是多端同时「操作」：手机按停止、电脑同时按继续，两条指令顺序不确定。这回到前文：操作进服务端排成全序，后到达的赢（LWW），各端按事件流收敛到同一状态。看是便宜的，写才需要仲裁。

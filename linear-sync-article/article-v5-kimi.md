# 断网改、换设备改、两人同时改，凭什么不乱？

用过多端工具的人多少踩过这几种坑：电脑上刚改完，手机上还是旧的；地铁里断网改了几条，到家联网全丢了；两个人同时改一个字段，后保存的把先保存的冲掉，谁都不记得自己赢过还是输过。

根源在架构的默认值：状态的真相只存在服务端，每次操作都是一次完整的网络往返。网络一不可靠，修改就丢、就乱、就冲突。

Linear 不这样。它的客户端断网照样改数据，联网后自动追平，多人同时在线也不打架。前段时间有人把它的客户端同步引擎 LSE（Linear Sync Engine）逆向成了一份文档（GitHub: wzhudev/reverse-linear-sync-engine），Linear CTO 公开评价它是「现存最好的文档，包括内部文档」。

支撑这套体验的是 local-first 架构：浏览器本地（IndexedDB）保留一份完整、可读写的状态副本，操作先写本地、界面立刻生效，网络退成后台同步管道。代价是多端各自改各自的，副本会分叉，需要一套同步机制来对账。LSE 就是这套机制。我把文档读了一遍，它其实就在回答四个问题。

## 一、本地修改频繁，怎么做到不等网络？

改个负责人、拖个状态，每次都转半秒圈，一天下来光等就几十分钟。Linear 的原则是界面响应永远不等网络。比如把 Issue 负责人改成 Bob，内存模型立即变，界面同步显示 Bob。同时把一条 Transaction 写进 IndexedDB 队列，随后批量发往服务端。

```text
用户操作
   ↓
内存模型立即改        ← 用户看到的
   ↓
Transaction 入队      ← IndexedDB 持久化
   ↓
批量发 Server
```

乐观更新只改内存，IndexedDB 只写服务端确认过的状态。这个边界让「用户看到的」和「服务端承认的」各归各位。

## 二、网络不可靠，一次操作有多少种走法？

这是整个引擎存在的原因。没有队列，一次点击只有一条开心路径：发出、收到、成功。但网络让现实多出好几种走法：

- 断网，请求根本没发出去；
- 丢包，服务端没收到；
- 服务端处理完了，响应丢在路上，客户端不知道成没成；
- 响应太慢，用户又点了两下；
- 你的请求还在飞，别人的变更先到了；
- 服务端收到了，但权限不够，拒绝。

队列的职责是给每条走法一个确定的结局，而不是祈祷走开心路径。丢了的走 Retry：Transaction 持久化在本地队列里，网络恢复重发，重启 App 也还在。被拒的走 Rollback：Transaction 存着修改前的旧值，把内存撤回去；本地数据库从没被提前改过，撤回只动内存，不牵扯数据修复。别人先到的走 Rebase：你那条「从 Tom 改成 Bob」的修改被重新解释成「从 Alice 改成 Bob」，界面继续显示 Bob，意图不被冲掉。

丢、拒、交错各有确定的结局，用户看到的东西才可信。

## 三、多端同时在线，怎么对账、冲突谁说了算？

LSE 给服务端的每个变更分配一个全局递增的 syncId。客户端只需在本地记一个数字：lastSyncId。

```text
Server:  100 ─ 101 ─ 102 ─ 103 ─ 104
                ↑
Client:  lastSyncId = 100，补齐 101~104
```

断线重连、换设备、打开半年没用的电脑，都是同一句话：向服务端请求 lastSyncId 之后的变更。实时推送走 WebSocket，syncId 就是用来对账和补课的游标。

这里区分两个概念：Transaction 代表客户端意图（「我要做什么」），Delta 代表服务端事实（「实际发生了什么」）。客户端发一条创建 Issue 的 Transaction，服务端可能顺手写入 history 并更新计数器。返回的 Delta 比 Transaction 多出一串副作用，客户端最终以 Delta 为准。

冲突由服务端仲裁：所有 Transaction 排成全序，同一字段的并发修改以后到达服务端的为准（Last Writer Wins）。注意顺序按到达服务端的时间算，不是点击时间。A 在 10:00:00 点击 Done，B 在 10:00:01 点击 Cancelled，若 B 先到，B 分到 100，A 分到 101，最终状态是 Done。服务端定胜负，客户端 Rebase 只管在结果出来前别让界面乱掉。

## 四、几十万个对象，怎么不卡？

一个大型 workspace 动辄几十万个对象，每个端全量拷贝一份，内存和流量都扛不住。LSE 从两个维度控制数据流向：

- **Sync Scope 决定能不能同步**：受权限、workspace、sync group 限制，不在授权范围内的变更绝不下发。
- **Load Strategy 决定什么时候加载**：每个模型元数据中定义加载策略：instant 启动即载，lazy 用到才载，partial 只载部分，explicitlyRequested 显式请求才载，local 只留本地。Issue 标题和状态是 instant，history 则是 explicitlyRequested。打开首页，客户端只拿渲染列表必需的几个字段。

Sync Engine 管「哪些数据要保持一致」，Lazy Loading 管「哪些数据当下值得加载」。

## 收个尾

丢、乱、冲突、卡，追到底都是同一张不可靠的网络闹的。把网络从操作的必经之路上拿掉，操作先落本地、按序对账、用到才载，它们就一起消失。

对照检查自己的产品：

- 用户操作需要等网络返回吗？
- 断网时的修改，重启 App 后还在吗？
- 网络失败和服务端拒绝，处理路径分开了吗？
- 别人的修改先到，会冲掉用户刚改的东西吗？
- 多端对账靠全量拉取，还是靠一个递增数字？
- 首屏只加载渲染必需的数据吗？

顺带说一句延伸：这套机制和 AI 无关，但长时间运行的 AI Agent 应用恰好缺的就是它。Agent 跑八分钟，Run 的状态只活在一条 SSE 连接里，用户刷新一下就全没了。同样的病，同一副药。

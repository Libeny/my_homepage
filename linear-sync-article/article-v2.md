# Agent 跑到一半网页刷新了，然后呢？

做 AI 应用的大多经历过这个场景：Agent 跑了八分钟，调了六次工具，刚写出一半代码，用户手滑刷新了页面。SSE 连接一断，中间状态全丢。只能把请求重新发一遍，再等八分钟。token 烧了，用户也走了。

根源不在网络波动，而在交互设计：我们习惯把长达数分钟的 Agent Run 当成一次普通 HTTP 请求。连接断了，就只能从头重来。

Linear 不用重来。它的客户端断网照样能改数据，重新联网后自动追平。背后的核心是它的同步引擎 LSE（Linear Sync Engine）。前段时间有人把 LSE 逆向成了一份文档（GitHub: wzhudev/reverse-linear-sync-engine），Linear CTO 公开评价它是「现存最好的文档，包括内部文档」。我把文档和源码读了一遍，顺着思路往 AI Agent 应用推了一步。

LSE 的核心是三件事：本地事务队列、全局递增序号同步、按需加载。

## 一、本地事务队列：先改内存，再排队

用户在界面上点一下，不应该等网络返回。

把 Issue 负责人改成 Bob，内存里的模型立即更新，界面同步显示 Bob。与此同时生成一条 Transaction，持久化进 IndexedDB 的队列，随后批量发给服务端。

```text
用户操作
   ↓
内存模型立即改        ← 用户看到的
   ↓
Transaction 入队      ← IndexedDB 持久化
   ↓
批量发 Server
```

这里的关键在于：乐观更新只改内存，本地数据库（IndexedDB）只写服务端确认过的状态。这个边界把失败处理变得很干净。

失败分两类，处理方式完全不同：

- **网络失败**：服务端根本没收到。Transaction 还留在本地队列里，等网络恢复后重发。重启 App 也丢不掉，因为队列是持久化的。断网时用户可以继续干活，操作一条条在本地攒着。
- **服务端拒绝**：权限不足或状态不允许。这才是真正的 Transaction 失败。Transaction 记录着修改前的旧值，触发 rollback 把内存状态撤回去。因为本地数据库从没被提前修改过，撤回只动内存，不涉及脏数据修复。

简言之：网络失败走 Retry，服务端拒绝走 Rollback。

还有一种并发中间态：你的 Transaction 还没被服务端处理，别人的修改先到了。服务端把别人的 Delta 推给你，如果直接覆盖内存，你刚改的 Bob 就会被冲掉。LSE 的解法是 Rebase：把你那条「从 Tom 改成 Bob」的 Transaction，重新解释成「从 Alice 改成 Bob」。界面继续显示 Bob，你的修改意图得以保留。

## 二、全局序号：用一个递增数字追平状态

多端同时在线时，客户端必须清楚自己遗漏了哪些数据变更。

LSE 给服务端的每个变更分配一个全局递增的 syncId。客户端只需记录一个数字：lastSyncId。

```text
Server:  100 ─ 101 ─ 102 ─ 103 ─ 104
                ↑
Client:  lastSyncId = 100，补齐 101~104
```

断线重连、换设备、打开半年没用的电脑，逻辑完全一致：向服务端请求 lastSyncId 之后的变更。实时推送走 WebSocket，syncId 就是游标，专门用来对账和补课。

这里需要区分两个概念：Transaction 代表客户端意图（「我要做什么」），Delta 则代表服务端的客观状态（「实际发生了什么」）。客户端发一条创建 Issue 的 Transaction，服务端执行时可能伴随生成 history、activity 并更新计数器。返回的 Delta 会比你的 Transaction 多出一长串副作用，客户端最终以 Delta 为准。

并发冲突由服务端仲裁。服务端把所有 Transaction 排成全序，同一字段的并发修改以「后到达服务端的为准」（Last Writer Wins）。注意这里的顺序由到达服务端的时间决定，而非点击时间。A 在 10:00:00 点击 Done，B 在 10:00:01 点击 Cancelled，若 B 的请求先抵达，B 分配到 100，A 分配到 101，最终状态是 Done。

分工很清晰：服务端定胜负，客户端 Rebase 只管在胜负定下之前别让本地界面跳变。

## 三、按需加载：一百万条数据不进浏览器

一个大型 workspace 往往有几十万个对象，客户端不可能把所有数据都塞进浏览器。

LSE 在两个维度上控制数据流向：

- **Sync Scope 决定能不能同步**：受权限、workspace、sync group 限制，不在授权范围内的数据绝不下发。
- **Load Strategy 决定什么时候加载**：每个模型的元数据中定义了加载策略——instant 启动即载，lazy 用到才载，partial 只载部分，explicitlyRequested 显式请求才载，local 只留本地。Issue 的标题和状态是 instant，而 history 属于 explicitlyRequested。用户打开首页，浏览器只拿渲染列表必需的几个字段。

Sync Engine 管「哪些数据要保持一致」，Lazy Loading 则管「哪些数据当下值得加载」。

## 把这三件套搬到 AI Agent

回到开头的故障场景。Agent Run 绝不是一次普通的 HTTP 请求，而是一条持续演进的状态流：创建任务、制定计划、调度工具、获取结果、继续推理。整个过程往往持续几分钟甚至数小时，中间不断产生新的状态。如果继续按照短请求模式设计，一旦连接断开，就会陷入无法恢复的僵局。

LSE 的三件套几乎可以直接平移：

| Linear | AI Agent |
|---|---|
| Issue 状态 | Agent Task 状态 |
| Transaction | 用户操作 / Agent 动作 |
| syncId | 事件序号 |
| Delta | Agent 事件 |
| 本地数据库 | 本地 Agent State |
| Transaction Queue | 待发送的用户输入 |
| Rebase | 事件重放、状态对账 |
| Lazy Loading | 按需加载工具结果和上下文 |

具体到接口设计上，不要只提供一个 `POST /agent/run` 挂着 SSE 长连接干等，而是拆为两步。

先创建任务：

```text
POST /tasks        → 拿到 Task ID = 123
```

服务端在后台执行并持续产生带序号的事件：

```text
seq=100  task.created
seq=101  agent.started
seq=102  planning.completed
seq=103  tool.call
seq=104  tool.result
...
```

客户端只需要在本地记录一个 lastSeq。网络中断、刷新页面或者切换到移动端，都统一发送同一个补齐请求：

```text
GET /tasks/123/events?after=105
```

服务端把 seq 106 之后的增量事件直接返回，客户端界面接着推进，Agent 完全不需要重跑。

在这个架构里，SSE 或 WebSocket 只是下发增量事件的实时管道，连接断开不会丢失系统状态。系统的可靠性不再依赖物理连接是否存活，而是依托于事件流、递增序号、本地状态与可重放机制。

相比 Linear，AI Agent 还多了一层复杂度。Linear 同步的是静态业务实体（Issue、Comment、Project），而 AI Agent 同步的则是完整的动态过程：任务阶段、工具调用的入参和返回值、多轮推理过程以及人工审批拦截。它需要的是一个面向执行过程的状态同步引擎。

## 带走一张检查清单

给你的 AI 应用做一次对照检查：

- Agent Run 拥有全局递增的事件序号吗？
- 断线或刷新后能直接通过 after=lastSeq 增量补齐，还是只能彻底重跑？
- 用户追加的输入在网络抖动时支持本地排队吗？
- 页面刷新后，已完成的工具调用入参和返回结果还在吗？
- 切换其他设备登录，能否直接看到同一任务的实时进度？

五条里若缺了一条，缺的往往就是 LSE 三件套里对应的机制。

把 Agent Run 从单次长连接请求，重构为可同步、可恢复、可回放的状态流。一旦完成了这种解耦，重连恢复、页面防刷、多端协同乃至审计重放，都能在同一套体系下顺理成章地解决。

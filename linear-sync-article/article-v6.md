# Linear 同步引擎深读：断网改、换设备改、两人同时改，凭什么不乱？

通读了 wzhudev 逆向 Linear 客户端同步引擎（LSE）的文档（GitHub: wzhudev/reverse-linear-sync-engine，Linear CTO 评价它是「现存最好的文档，包括内部文档」）。它表面上在解释 Linear 为什么丝滑，实际给出的是一份完整答案：多端在线、修改频繁的场景下，修改怎么做到不丢、不乱、不冲突。

## 一、几个眼熟的事故

电脑上刚改完，手机上还是旧的；地铁里断网改了几条，到家联网全丢了；两个人同时改一个字段，后保存的把先保存的冲掉，谁都不记得自己赢过还是输过。

根源是架构的默认值：状态的真相只存在服务端，每次操作都是一次完整的网络往返。网络一不可靠，修改就丢、就乱、就冲突。

Linear 的做法是 local-first：浏览器本地（IndexedDB）留一份完整、可读写的状态副本，操作先写本地、界面立刻生效，网络退成后台同步管道。代价是多端各自改各自的，副本会分叉，需要一套同步机制对账——LSE 就是这套机制。

## 二、花名册：四个角色，各管一段

LSE 拆成四件事：事务队列管上行，你的修改怎么出去；全局序号管下行，别人的变更怎么进来；Rebase 管交错，两边撞车怎么办；按需加载管流量，几十万个对象怎么不卡。下面逐个点名。

## 三、事务队列：先改内存，再排队

改个负责人、拖个状态，如果每次都转半秒圈，一天下来光等就几十分钟。Linear 的原则是界面响应永远不等网络。把 Issue 负责人改成 Bob，内存模型立即变，界面同步显示 Bob；同时一条 Transaction 写进 IndexedDB 队列，随后批量发往服务端。

```text
用户操作
   ↓
内存模型立即改        ← 用户看到的
   ↓
Transaction 入队      ← IndexedDB 持久化
   ↓
批量发 Server
```

乐观更新只改内存，IndexedDB 只写服务端确认过的状态——「用户看到的」和「服务端承认的」各归各位。

这条队列不是设计图，打开 DevTools 的 IndexedDB 就能看见它。`_transactions` 表里躺着一条真实的缓存：

```text
{ id: 1, type: "update", modelClass: "Issue",
  modelId: "bda1a998-…", changeSnapshot: { changes: … } }
```

你的每一次点击都是这样一个对象：先落本地，再上路。

## 四、一次操作有六种走法

这是整个引擎存在的原因。没有队列，一次点击只有一条开心路径：发出、收到、成功。但网络让现实多出好几种走法：

- 断网，请求根本没发出去；
- 丢包，服务端没收到；
- 服务端处理完了，响应丢在路上，客户端不知道成没成；
- 响应太慢，用户又点了两下；
- 你的请求还在飞，别人的变更先到了；
- 服务端收到了，但权限不够，拒绝。

队列的职责不是祈祷走开心路径，而是给每条走法一个确定的结局。丢了的走 Retry：Transaction 持久化在本地，网络恢复重发，重启 App 也还在。被拒的走 Rollback：Transaction 存着修改前的旧值，把内存撤回去；本地数据库从没被提前改过，撤回只动内存，不牵扯数据修复。别人先到的走 Rebase：你那条「从 Tom 改成 Bob」被重新解释成「从 Alice 改成 Bob」，界面继续显示 Bob，意图不被冲掉。

还有一个不显然的好处：Transaction 按可逆设计，每条都存着旧值和 changeSnapshot，Linear 的 undo/redo 是这套队列白送的。

## 五、全局序号：对账不靠拉全量，靠一个数字

打开半年没用的电脑，客户端怎么知道自己漏了什么？LSE 给服务端的每个变更分配一个全局递增的 syncId，客户端只记一个数字：lastSyncId。

```text
Server:  100 ─ 101 ─ 102 ─ 103 ─ 104
                ↑
Client:  lastSyncId = 100，补齐 101~104
```

断线重连、换设备，都是同一句话：向服务端请求 lastSyncId 之后的变更。实时推送走 WebSocket，syncId 就是用来对账和补课的游标。

文档里有张手绘图，标出了真实序号的规模——已经排到 23466457。图里两个细节值得看：delta packet 广播给所有在线端，包括发起的那台自己（客户端意图和服务端事实不是一回事，以服务端事实为准）；时间轴上别的 workspace 的变更也占编号，序号是全系统共用的一条数轴，不只数你自己的修改。

## 六、冲突谁说了算：服务端

Transaction 代表客户端意图（「我要做什么」），Delta 代表服务端事实（「实际发生了什么」）。你发一条创建 Issue 的 Transaction，服务端执行时可能顺手写入 history、更新计数器，返回的 Delta 比你发出的东西多一串副作用。客户端最终以 Delta 为准。

同一字段的并发修改，规则是 Last Writer Wins——但「后」按到达服务端的时间算，不是点击时间。A 在 10:00:00 点 Done，B 在 10:00:01 点 Cancelled，若 B 先抵达，B 分到 100，A 分到 101，最终状态是 Done。服务端定胜负，客户端的 Rebase 只管在结果出来之前别让界面乱掉。

## 七、几十万个对象，怎么不卡

一个大型 workspace 动辄几十万个对象，每个端全量拷贝一份，内存和流量都扛不住。LSE 在两个维度上卡数据流向：

- **Sync Scope 决定能不能同步**：受权限、workspace、sync group 限制，不在授权范围内的变更绝不下发。
- **Load Strategy 决定什么时候加载**：每个模型在元数据里声明加载策略：instant 启动即载，lazy 用到才载，partial 只载部分，explicitlyRequested 显式请求才载，local 只留本地。Issue 标题和状态是 instant，history 是 explicitlyRequested。打开首页，客户端只拿渲染列表必需的几个字段。

元数据不靠约定靠代码：模型用装饰器把 loadStrategy 注册进一张全局的 ModelRegistry，启动时先建这张表。加载进内存的模型统一进 Object Pool 按 UUID 索引，属性支持懒水合——用到哪个字段，再 hydrate 哪个。

Sync Engine 管「哪些数据要保持一致」，Lazy Loading 管「哪些数据当下值得加载」。

## 八、代价与边界

这套东西不是免费的，学之前先看账单：

- **复杂度搬了家**：本地副本、队列、对账逻辑全在客户端，你的前端从此是一个有状态的数据库客户端，不再是渲染层。Linear 光启动流程（bootstrapping）画出来就是一张密不透风的图。
- **冲突只能仲裁，不能消灭**：LWW 意味着总有人被覆盖。Linear 敢这么选，赌的是同一字段的并发修改极少见。协作编辑文档别学这个，那需要 OT 或 CRDT。
- **undo 要从第一天预留**：Transaction 的可逆设计是 undo/redo 的地基，后补补不上。

判断标准一句话：这套机制的收益和「修改频率 × 端数」成正比。内容站、单端工具、一年改不了几次的后台，都不需要它。

## 九、设计启示

- **把网络从操作的必经之路上拿掉**。丢、乱、冲突、卡，都是同一张不可靠的网闹的；操作先落本地、按序对账、用到才载，它们一起消失。
- **上行和下行分开想**。上行要的是「每条走法有确定结局」（队列 + retry/rollback/rebase），下行要的是「知道自己漏了什么」（序号 + 对账）。混在一起设计，两头都做不干净。
- **服务端是唯一裁判**。客户端可以乐观、可以重放，但最终状态以 Delta 为准。

顺带一句延伸：这套机制和 AI 无关，但长时间运行的 AI Agent 应用恰好缺的就是它——Agent 跑八分钟，Run 的状态只活在一条 SSE 连接里，用户刷新一下就全没了。同样的病，同一副药。

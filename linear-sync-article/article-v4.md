# Agent 跑到一半网页刷新了，然后呢？

做 AI 应用大多经历过这个场景：Agent 跑了八分钟，调了六次工具，刚写出一半代码，用户手滑刷新了页面。SSE 连接一断，中间状态全丢。只能重新发一遍请求，再等八分钟。token 烧了，用户也走了。

根源在交互设计：我们习惯把耗时几分钟的 Agent Run 粗暴当成一次普通 HTTP 请求。连接断了，就只能从头重来。

我在做 AI 应用时正卡在这里。当时在 X 上刷到一份逆向工程文档（GitHub: wzhudev/reverse-linear-sync-engine），逆向的是 Linear 客户端同步引擎 LSE（Linear Sync Engine）。Linear CTO 公开评价它是「现存最好的文档，包括内部文档」。传统 Web 应用的状态全在服务端，每次操作的延迟下限是一次网络往返，断网就瘫痪。Linear 采用的 local-first 架构把逻辑倒了过来：浏览器本地（IndexedDB）保留一份完整、可读写的状态副本，操作先写本地、界面立刻生效，网络退成后台同步管道。代价是多端本地修改会分叉，需要一套同步机制来对账——LSE 就是这套机制。但 Linear 的计算在客户端，Agent 的计算必须在服务端，整套 local-first 搬不过来，能搬的是它的状态同步模型。我卡着的问题里，有两个正好归它管：断线刷新后状态怎么接上，执行内容变多后怎么保证速度。

## 一、刷新、断网、换设备，Agent 跑到哪了怎么接上？

Agent 跑几分钟，用户不可能一直盯屏幕。进电梯断网、地铁弱网或换手机，连接断了之前的执行算不算数？进度怎么接上？多数应用要么全丢，要么最后甩个大 JSON，中间过程全断了档。

Linear 的解法是给服务端每个变更分配一个全局递增的 syncId。客户端只需在本地记一个数字：lastSyncId。

```text
Server:  100 ─ 101 ─ 102 ─ 103 ─ 104
                ↑
Client:  lastSyncId = 100，补齐 101~104
```

断线重连、换设备、打开半年没用的电脑，都是同一句话：向服务端请求 lastSyncId 之后的变更。实时推送走 WebSocket，syncId 就是用来对账和补课的游标。

这里区分两个概念：Transaction 代表客户端意图（「我要做什么」），Delta 代表服务端事实（「实际发生了什么」）。客户端发一条创建 Issue 的 Transaction，服务端可能顺手写入 history 并更新计数器。返回的 Delta 比 Transaction 多出一串副作用，客户端最终以 Delta 为准。

平移到 AI Agent：把执行生命周期拆成带序号的事件流。刷新页面或换设备打开，客户端拿着本地 lastSeq 发请求：

```text
GET /tasks/123/events?after=105
```

服务端补齐 106 之后的事件，客户端对账重放，界面立刻还原到当前进度，Agent 不用重跑。

## 二、执行过程内容太多，全加载就慢，怎么保证速度？

复杂任务调几次工具就吐出成千上万行数据，两头都卡：服务端给模型准备 context 要挑，不能全灌进 prompt；客户端渲染也要挑，全推给浏览器首屏立刻卡死。但若全丢掉，排查时又看不到入参和返回值。

Linear 在客户端面对同样的问题：一个大型 workspace 动辄几十万个对象，客户端装不下。LSE 从两个维度控制数据流向：

- **Sync Scope 决定能不能同步**：受权限、workspace、sync group 限制，不在授权范围内的变更绝不下发。
- **Load Strategy 决定什么时候加载**：每个模型元数据中定义加载策略：instant 启动即载，lazy 用到才载，partial 只载部分，explicitlyRequested 显式请求才载，local 只留本地。Issue 标题和状态是 instant，history 则是 explicitlyRequested。用户打开首页，浏览器只拿渲染列表必需的几个字段。

Sync Engine 管「哪些数据要保持一致」，Lazy Loading 管「哪些数据当下值得加载」。

平移到 AI Agent：在两端按需切分。给模型准备上下文时，历史步骤只传摘要，详细输出按需检索；给前端推送时，默认只推状态概要（instant），几万行工具输出和推理树标为 explicitlyRequested，用户点击展开再拉取。模型窗口与浏览器内存都不会被撑爆。

## 三、合拢：能搬的那一半

回头看，LSE 里有一半搬不过来——事务队列、乐观更新、Rebase，解决的都是「计算在客户端」才有的问题，Agent 用不上；能搬的是状态同步模型：事件流、递增序号、对账重放、按需加载。

接口设计上拆成两步，不要只提供单个 `POST /agent/run` 挂长连接干等。先创建任务：

```text
POST /tasks        → 拿到 Task ID = 123
```

服务端在后台推进，持续产生带序号的事件流：

```text
seq=100  task.created
seq=101  agent.started
seq=102  planning.completed
seq=103  tool.call
seq=104  tool.result
...
```

在这个体系下，SSE 或 WebSocket 只是实时管道，断了就断了，哪怕纯靠轮询对账也能追平。系统的可靠性立在事件流、递增序号、本地状态与重放机制上。

AI Agent 比传统协作软件多同步一层：Linear 同步的是业务数据（Issue、Comment、Project），AI Agent 还要同步执行过程（任务计划、工具调用的入参和返回值、推理中间态以及人工审批断点）。它同步的不只是最终结果，更是完整的执行现场。

## 四、两个追问

### 追问一：SSE 断了，订阅怎么恢复？

SSE 协议自带恢复机制：服务端给每条事件带上 `id:` 字段，浏览器 EventSource 断线会自动重连，并把收到的最后序号放进 `Last-Event-ID` 请求头，重连不用造轮子。

但请求头只告诉服务端看到第几笔，能不能补齐取决于事件流有没有落库。若是内存转发、发完即弃，连上也无从补起。防范 TCP 半开（连接没断却卡住），服务端定期发心跳（SSE 里一行 `: ping` 注释），客户端超时未收到数据就主动断开重连。SSE 负责断了自动再接，序号加事件日志负责从哪补——前者协议白给，后者架构里必须有。

### 追问二：电脑和手机同时看一个 Run 的实时过程，两条 SSE 一样吗？

多端查看不需要新机制。每条 SSE 是独立的 HTTP 响应，两台设备各自连 `GET /tasks/123/events`，服务端把同一条事件流扇出给两条连接，内容完全一样。游标 lastSeq 记在各端本地，谁掉线谁拿 `?after=lastSeq` 补课。工程上 worker 的事件只产生一次并写入日志（可借由 Redis pub/sub 扇出），不必为每个客户端各跑一遍。

真正需要额外机制的是多端同时操作：手机按停止、电脑同时按继续。多端操作进入服务端排成全序，后到达的指令生效，各端再随事件流对账收敛。看是便宜的，写才需要仲裁。

## 五、带走一张检查清单

对照检查你的 AI 应用：

- Agent Run 有全局递增的事件序号吗？
- 断线或刷新后能用 after=lastSeq 增量补齐，还是只能从头重跑？
- 页面刷新后，已完成的工具调用入参和返回结果还在不在？
- 换一台设备登录，能否看到同一个任务走到哪一步？

四条里缺了哪一条，对应的就是状态同步模型里缺的那一块。

把 Agent Run 从单次长请求重构为带序号的状态流。网络重连、页面防刷与多端对账，便只是这套机制自然带出的基本能力。

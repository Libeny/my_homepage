Pi 学习探索：为什么它是搞懂 Agent 底层与面试的最佳代码库

以 Pi-Mono 为模板，深入拆解 Agent Runtime 底座

在 Agent 系统设计与面试中，最常见的瓶颈是“概念听过很多，但一落地就卡在细节”：网上的极简 while (true) 无法应对打断、插话、流式半截 JSON 和长程爆窗；而成熟产品又被深度封装成黑盒。开源的 pi-mono 恰好处在一个极佳的位置——源码干净透明，却完整实现了工业级 Agent 该有的核心调度机制。从最简循环出发，我们将顺着真实的工程问题，一步步推导出它的完整形态。

一、原点：Coding Agent 最纯粹的心脏

无论是 Claude Code、Codex，还是其他自主智能体，底层都有一个很简单的 Agent Loop：模型先判断下一步，再调用工具行动；工具结果回来后，模型根据新信息继续判断。

STEP 0 · 核心闭环 AGENT LOOP

思考 → 行动 → 观察 → 再思考
Think → Act → Observe → Repeat
当模型不再需要调用工具时，它给出当前回复，这一轮通常就结束了。

01-基础循环.ts
// Step 0: 最简状态的 Agent Loop 骨架
async function runMinimalAgent(messages, tools) {
  while (true) {
    // 1. 思考：模型判断下一步 (Think)
    const assistant = await llm.call(messages, tools);
    messages.push(assistant);

    // 2. 判断：若不需要调用工具，给出最终回复，本轮结束
    if (!assistant.toolCalls || assistant.toolCalls.length === 0) {
      break;
    }

    // 3. 行动：调用工具执行 (Act)
    const toolResults = [];
    for (const call of assistant.toolCalls) {
      const result = await executeTool(call);
      toolResults.push(result);
    }

    // 4. 观察：拿到新信息，写回历史准备再思考 (Observe ➔ Repeat)
    messages.push(...toolResults);
  }
}

尽管这段极简循环在概念上完全跑得通，然而在真实使用中，人机协作和工程运行会有截然不同的诉求：用户会想实时纠偏、随时喊停、连续排队，系统还需要流式打字与长期记忆防爆窗。下面，我们就跟随这些真实诉求，一步步把代码演进出来。

二、第一步演进：给循环装上“刹车”与“方向盘”（人类介入）

在实际使用中，人类绝不会只是在旁边当观众。人类与 Agent 的交互主要有两种行为：“踩刹车” 与 “打方向盘”。

诉求 1 · 踩刹车 (Abort) COOPERATIVE CANCELLATION
🤖 AGENT [Tool: bash("npm run test:all")] 正在执行全量测试套件（预计耗时 5 分钟）...
👤 人类用户 [按下了 Ctrl+C / 点击了界面的 🛑 停止生成 按钮]
⚠️ 翻车时刻：虽然 UI 界面显示已停止，但后台子进程并没有收到退出信号，CPU 依然 100% 狂转，模型还在后台持续吐 Token 扣费...

解法：取消不是前端改个状态，必须全链路贯穿标准 AbortSignal，穿透打断 HTTP 客户端与底层工具子进程。

诉求 2 · 打方向盘 (Steering) IN-FLIGHT STEERING
🤖 AGENT 收到！我将分 5 步重构认证模块：1. 读代码 2. 改全局配置文件 3. 改登录路由... 正在执行第 1 步...
🤖 AGENT [Tool: read_file] 第 1 步完成。紧接着开始第 2 步，准备修改全局 config/app.yaml...
👤 人类用户（焦急打字中） 等等！千万别动全局 config！只改模块局部的参数传参就行！
⚠️ 翻车时刻：Agent 在 while(true) 中自顾自狂奔，完全没看用户的插话，直接把全局配置给覆盖了...

解法：在工具执行完毕后、下一次调用模型之前设置拦截检查点，把用户实时的纠偏指令（Steering）注入 Context，让模型在下一轮思考时自然调整航向。

02-刹车与方向盘.ts
async function runInteractiveAgent(context, config, signal: AbortSignal) {
  while (true) {
    // 【刹车】：检查取消信号
    if (signal.aborted) {
      emit("agent_aborted");
      return;
    }

    // 【方向盘】：在模型思考前，优先注入用户的实时纠偏指令
    const steeringMessages = await config.getSteeringMessages?.() ?? [];
    if (steeringMessages.length > 0) {
      context.messages.push(...steeringMessages);
    }

    // 将 signal 穿透传递给大模型（可中断 HTTP 请求）
    const assistant = await llm.call(context.messages, config.tools, { signal });
    context.messages.push(assistant);

    if (assistant.stopReason === "aborted" || assistant.stopReason === "error") {
      return;
    }

    if (!assistant.toolCalls?.length) break;

    // 将 signal 穿透传递给工具（可中断底层子进程/网络任务）
    const toolResults = await executeTools(assistant.toolCalls, { signal });
    context.messages.push(...toolResults);
  }
}

现在，我们已经有了在单次任务中随时“喊停（Abort）”和“微调方向（Steering）”的能力。但如果用户在 Agent 干活时不是想就地纠偏，而是想排队安排下一个完全不同的任务呢？单层循环在语义上就无法区分了——这引出了下一步：双层循环的诞生。

三、第二步演进：任务串联与排队（双层循环的诞生）

认知升级 · 消息性格分流 STEERING VS FOLLOW-UP
💬 消息类型 A：实时插话 (Steering - 当前任务纠偏) “等等，改完函数顺便把入参校验加上。” ➔ 期望：立即介入当前这一轮修改！
💬 消息类型 B：后续排队 (Follow-up - 下一工单) “等上面所有修改和测试都跑通后，帮我给群里发个部署完成卡片。” ➔ 期望：当前任务彻底收敛结束后再开始！

如果只有一层 while (true)，很难表达“当前任务完全收敛后，再消费下一个任务”的排队语义。Pi 在这里设计了非常优雅的双层循环结构：
• 内层循环（单任务工单冲刺）：专心把当前这件事干完（连续 Tool Calls + Steering 纠偏）；
• 外层循环（任务调度派发台）：内层自然结束后，检查有没有排队的 Follow-up，有则重新唤醒内层。

03-双层循环调度.ts
async function runDualLoopAgent(context, config, signal) {
  let pendingMessages = await config.getSteeringMessages?.() ?? [];

  // 【外层循环】：负责拉取后续排队的 Follow-up 任务
  while (true) {
    let hasMoreToolCalls = true;

    // 【内层循环】：当前任务冲刺（消费连续 Tool Calls 与 Steering 插话）
    while (hasMoreToolCalls || pendingMessages.length > 0) {
      if (signal.aborted) return;

      if (pendingMessages.length > 0) {
        context.messages.push(...pendingMessages);
        pendingMessages = [];
      }

      const assistant = await llm.call(context.messages, config.tools, { signal });
      context.messages.push(assistant);

      if (assistant.stopReason === "error" || assistant.stopReason === "aborted") return;

      const calls = assistant.toolCalls ?? [];
      let toolResults = [];
      hasMoreToolCalls = false;

      if (calls.length > 0) {
        toolResults = await executeTools(calls, { signal });
        context.messages.push(...toolResults);
        hasMoreToolCalls = !toolResults.every(r => r.terminate);
      }

      // 内层工具批次跑完，下一次思考前优先检查 Steering 实时纠偏！
      pendingMessages = await config.getSteeringMessages?.() ?? [];
    }

    // 内层结束了（当前任务已彻底完成）
    // 此时外层检查是否有排队的后续任务（Follow-up）
    const followUps = await config.getFollowUpMessages?.() ?? [];
    if (followUps.length > 0) {
      pendingMessages = followUps;
      continue; // 重新唤醒内层循环！
    }

    break; // 既无内层任务，也无 follow-up，彻底收工
  }
}

双层循环让 Agent 具备了持续自主推进多任务的能力。但随之而来的代价是：随着工具连续调用和任务串联，消息历史（Transcript）迅速膨胀。如果不做干预，几十轮后就会直接撑爆模型的 Context Window。如何在不中断任务的前提下进行记忆压缩？这引出了下一步：上下文压缩机制（Compaction）。

四、第三步演进：长程运转的防爆窗机制（Compaction 压缩）

当 Agent 围绕双层循环连续跑了数十轮后，累积的会话历史（Transcript）会迅速逼近模型的 Context Window 上限（例如 128k）。如果不做干预，API 请求将直接因超长而报错挂掉。

很多人的第一反应是“把旧消息直接删掉”或者“发一句‘请总结以上对话’”。但生产级 Agent 的 Compaction 是一套非常严谨的记忆预算与安全置换机制，包含四个核心精髓：

  • 1. 检查与留足空间（Context Budget）：
    不是每轮都盲目压缩，而是为模型本轮输出与工具调用预留足够的安全余量（reserveTokens，如 16k）。当 CurrentTokens > ContextWindow - ReserveTokens 时才触发压缩。
  • 2. 安全切分线（Safe Boundary）：
    从后向前保留最近一段活跃原文（keepRecentTokens，如 20k），确保当前任务细节不丢。核心铁律：切分点绝不能落在 Tool Result 上，严禁切断 Tool Call 与 Result 的成对关系。
  • 3. 结构化增量摘要（Incremental Summary）：
    旧历史被序列化为紧凑纯文本，摘要请求显式关闭工具，且将上一次的旧摘要放入 <previous-summary> 要求模型增量更新，防止多轮后信息退化。
  • 4. 压缩后的有效上下文结构：
    压缩完成后，替换 context.messages，下一轮主模型看到的有效历史为：
    System Prompt + Compaction Summary + 最近保留的活跃原始消息。
04.1-上下文预算切分.ts
// 【核心函数】：接近窗口上限时，进行安全切分与置换
async function ensureContextBudget(context, config, signal) {
  const contextTokens = countTokens(context.messages);

  // 1. 检查：快到上限时才触发压缩
  if (contextTokens <= config.contextWindow - config.reserveTokens) return;

  // 2. 安全切分：从后向前保留最近消息，绝不切断 Tool Call 与 Result 的成对关系
  const { oldHistory, recentMessages } = splitAtSafeBoundary(
    context.messages,
    config.keepRecentTokens
  );

  // 3. 独立摘要：纯文本输入，显式关闭 tools，带入旧摘要增量合并
  const summary = await summarize({
    transcript: serializeForSummary(oldHistory),
    previousSummary: findPreviousSummary(oldHistory),
    tools: [],
    signal,
  });

  // 4. 组装新 Context：摘要 + 最近保留原文
  context.messages = [makeCompactionMessage(summary), ...recentMessages];
}

解决了循环控制、任务调度和长程记忆防爆窗之后，Agent 的逻辑骨架已经相当完整。但在真实的生产环境中，还有最后两个影响体验与稳定性的深水区问题需要跨越：前端打字机的流式体验与多工具并发时的时序确定性。

五、第四步演进：体验与稳定性的深水区（流式打字与保序写回）

在交互进入工程深水区后，我们需要解决最后两个关键矛盾：

  • 流式打字 vs 参数完整性：前端需要逐字打字（SSE 流），但工具必须拿到完整合法的 JSON 后才能执行；
  • 并发吞吐 vs 历史确定性：并发执行 3 个只读工具以提升速度，但如果按网络返回时间先后 push 进 Transcript，会导致历史乱序，破坏重放测试与单测断言。
05.1-流式响应.ts
async function streamAssistantResponse(context, config, signal) {
  let partial = createEmptyAssistantMessage();

  for await (const delta of llm.stream(context, { tools: config.tools, signal })) {
    partial = mergeDelta(partial, delta); // 持续累积 text、thinking 与 tool-call 参数
    emit("message_update", partial); // 实时派发事件供 UI 逐字渲染
  }

  return partial; // 流结束后返回完整消息，参数完全闭合可校验
}

六、最终形态：Pi-Mono 工业级控制流全景

至此，最初那段 20 行的极简循环，可以抽象为下面这份 Pi 风格的工程化等价伪代码：

06-完整循环.ts
// 最终形态：Pi 风格的工程化 Agent Loop（等价伪代码）
async function runLoop(context: AgentContext, config: AgentConfig, signal: AbortSignal) {
  let pendingMessages = await config.getSteeringMessages?.() ?? [];
  let firstTurn = true;

  // 【外层循环】：消费 Follow-up 队列
  while (true) {
    let hasMoreToolCalls = true;

    // 【内层循环】：消费 Steering 队列与连续工具调用
    while (hasMoreToolCalls || pendingMessages.length > 0) {
      emit("turn_start");
      firstTurn = false;

      // 1. 注入排队消息 (Steering / Follow-up)
      if (pendingMessages.length > 0) {
        for (const message of pendingMessages) {
          emit("message_start", message);
          emit("message_end", message);
          context.messages.push(message);
        }
        pendingMessages = [];
      }

      // 2. 下一次模型调用前，先保证 context 留有回答与工具调用的空间
      await ensureContextBudget(context, config, signal);

      // 3. 流式调用模型（内部派发 delta，此处 await 组装终态）
      const assistant = await streamAssistantResponse(context, config, signal);

      if (assistant.stopReason === "error" || assistant.stopReason === "aborted") {
        emit("agent_end");
        return;
      }

      const calls = assistant.toolCalls;
      let toolResults = [];
      hasMoreToolCalls = false;

      // 4. 安全执行工具
      if (calls.length > 0) {
        toolResults = assistant.stopReason === "length"
          ? failTruncatedToolCalls(calls)
          : await executeToolCalls(calls, { signal });

        hasMoreToolCalls = !toolResults.every(result => result.terminate);
        // 严格按照原始模型调用顺序写入 Transcript
        context.messages.push(...toolResults);
      }

      emit("turn_end", { assistant, toolResults });
      await config.prepareNextTurn?.({ assistant, toolResults, context });

      if (await config.shouldStopAfterTurn?.({ assistant, toolResults, context })) {
        emit("agent_end");
        return;
      }

      // 5. 工具批次执行完毕，下一次思考前优先检查 Steering
      pendingMessages = await config.getSteeringMessages?.() ?? [];
    }

    // 6. 内层结束，检查 Follow-up 队列
    const followUps = await config.getFollowUpMessages?.() ?? [];
    if (followUps.length > 0) {
      pendingMessages = followUps;
      continue;
    }

    break;
  }

  emit("agent_end");
}

七、总结：从演进中理解架构

  1. 一切始于 while (true)：Agent 的基石是“大模型决定下一步行动，直到无工具调用或显式结束”。
  2. 演进线清晰自然： 人类要介入 ➔ 引入 AbortSignal 刹车 与 Steering 方向盘；
    任务要排队 ➔ 引入 内层冲刺 + 外层调度 双层循环；
    长程不爆窗 ➔ 引入 带安全切分边界的 Compaction 压缩；
    体验与稳定 ➔ 引入 流式分流与严格保序写回。
  3. 把握了这条生长线，就看透了所有 Agent 架构的调度内核。

在下一篇中，我们将探讨在拥有了这样一个健壮底座后，如何通过替换 System Prompt + Compaction Prompt + Domain Tools + Durable State 以及多分支树状 Session，将它打造成完全属于你自己的垂直 Agent。
